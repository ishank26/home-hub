## Shared shopping

The deployed tablet now uses HA's existing Shopping list for names and completion
states, including phone-originated changes. Private config selects
`shopping.source = homeassistant`; `local` keeps the original tablet store.
The original local list is preserved and was not uploaded automatically.
Quantity, category and notes remain tablet-local metadata because the native HA
Shopping list does not provide those fields. Phone additions default to Other.

Reads refresh within fifteen seconds on the backend and on the UI's normal poll.
Writes require readback. Creates use a browser request key and bounded durable
receipts; an ambiguous create is never blindly repeated. An unresolved receipt
blocks further adds until its outcome is established from HA, rather than risking
duplicates. This is not an automatic offline-write queue: failed writes remain
unconfirmed and the UI offers Retry. The browser's last-good list stays stale
when HA is offline. Original local storage is a separate fallback source.
Delete Undo uses the returned item ID, retains its create key, and provides an
actual persistent Retry action if restoration fails. Concurrent phone edits do
not cause Undo to complete another item.

Live create, completion and deletion readbacks passed using one synthetic item;
only that test item was removed. Actual iPhone-app acceptance still needs the
owner to open HA Shopping and make an edit from that phone.

## Recipe reader research and implementation — 2026-10-18

Researched [recipe-scrapers](https://github.com/recipe-scrapers/recipe-scrapers),
the [Python original](https://github.com/hhursev/recipe-scrapers), and
[Mozilla Readability](https://github.com/mozilla/readability). Recipe-specific
Schema.org JSON-LD gives ingredients and ordered steps; general article extraction
can lose that structure and requires HTML sanitization. The implementation uses a
small independent stdlib parser for those structured fields. No third-party code
was copied or installed and no publisher HTML is rendered in the dashboard.

Fixed public HTTPS reads validate every resolved address and redirect, pin the
connection address, retain TLS hostname verification, reject internal/mapped IPs,
URL credentials and custom ports, and send no browser cookies or server secrets.
Concurrency, DNS jobs, redirects, response bytes, timeout and parser traversal are
bounded. Images/scripts/ads are not downloaded or executed by the browser. Five
recent extracted text recipes are kept in private runtime storage. Reader deep
links retain existing dashboard admission; this does not expose the hub publicly.

Synthetic HTTP/browser checks cover paste → import → focus → font changes → step
check-off → share/copy → reader deep link on desktop and mobile. Live structured
extraction succeeded on Love and Lemons' pancakes page (eight ingredients/five
steps). Budget Bytes refused automated access and the tested Good Food Middle
East page provided no supported metadata; both return honest errors. Site-specific
scrapers, login/paywall access and native iPhone share-target enrollment are not
implemented. Use the share link or paste a browser URL into Recipes.

| `camera.*` (local ONVIF) | available | — |

The three calendars failed within 25 s of each other, which points at the CalDAV
integration rather than at a single calendar or at Apple-side permission for one
shared calendar. The staggered failures across different integrations
(2026-10-18 16:59 → 2026-10-19 20:38) are consistent with HA's outbound cloud
sessions degrading one by one rather than with a host-level network fault:
`https://caldav.icloud.com/` answers HTTP 403 in 0.38 s from this host (a bare
root 403 is the expected Apple response), and the dashboard's own Open-Meteo
fetches stay `current`.

The dashboard is behaving correctly under the failure: `/api/status` reports
`calendar: failed`, `/api/today` returns `calendarSource: failed` with an empty
event list, `/api/home` marks the Twinkly light `available: false` with detail
`Unavailable`, and both cameras still return `available: true`. No sample data is
substituted for the failing sources.

Recovery is owner-local and needs an HA admin session or container access: reload
the CalDAV config entry and, if it reports an authentication error, replace the
Apple app-specific password; then reload Twinkly and Met.no. The homehub HA token
is deliberately non-admin, so `/api/error_log` returns 401 and config-entry reload
is unavailable from the dashboard credential — that isolation is working as
designed and was not bypassed for this audit.
